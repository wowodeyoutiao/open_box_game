# 单机化代码架构分层

> 时间：2026-10-25
> 触发问题：① 服务端配置表是否都要移植？② 逻辑不应全塞在本地消息层，结构需要梳理
> 结论：**配置表 90% 不用移植；但本地逻辑必须分层，LocalServer 只做路由，不写业务**

---

## 0. 总体判断

**合适，可以用。上一版有三处要修正，已改在下面正文里。**

### 这个方案的本质
把客户端改造成「**在本地完整模拟一遍 服务端 → 网络 → 客户端 的链路**」：
Service 扮演服务端算逻辑，LocalData 扮演数据库，推送扮演网络包，ProtoC 扮演收包端。

### 为什么这样最划算（而不是让 Service 直接改 Manager）

| 收益 | 说明 |
|---|---|
| **ProtoC + 128 个 UI 零改动** | 它们只认推送，不关心数据从哪来 |
| **可回退** | 将来要联网/上云端，把 LocalServer 换成真网络即可，客户端代码不动 |
| **存档边界清晰** | 只序列化 LocalData，Manager 是派生数据 |
| 数据流向单向 | 排查只需看一个方向 |

**代价是比"直接改 Manager"多约 30–50% 代码量**。考虑到要上 TapTap、将来可能加联网和云存档，这笔账划算。

### 三处修正

| # | 上一版的问题 | 修正 |
|---|---|---|
| 1 | 只说"LocalData 是唯一数据源"，**没说清它和 RoleM/BagM 的关系** | 明确为：LocalData = 模拟**服务端 DB**；RoleM/BagM = **客户端镜像**；中间由 ProtoC 的 `Sever_*Push` 连接（已用代码验证，该链路现成） |
| 2 | 建议"战斗核心走 AOT"，**过早定死** | 改为：**先放热更层，阶段 2 实测 WebGL 帧率后再决定**。查代码发现战斗是定时 tick 驱动，不是每帧，ILRuntime 压力可能没那么大 |
| 3 | 要求"Service 互不引用"，**不现实** | 改为：**允许单向依赖，禁止循环**。这个游戏角色↔装备↔伙伴↔战斗高度耦合，硬解耦会逼出一堆无意义转发层 |

## 2. 架构分层（这句话最重要）

> **LocalServer 是路由表，不是业务容器。**

现在只有 6 条协议，塞在一起还行。但全量是 **137 条路由 + 48 个 HTTP**，全写进去就是个上万行的上帝类，后面 7,400 行战斗逻辑再进来就彻底失控。

### 2.1 四层结构

```
┌─────────────────────────────────────────────────────────┐
│  Adapter 适配层（薄）                                    │
│  LocalServer.cs   ← CmdId → Service 方法，只做参数转换   │
│  LocalHttpRouter  ← URL → Service 方法                   │
│  规则：一行业务逻辑都不写                                 │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Service 领域服务层（业务都在这）                        │
│  PlayerService  角色/属性/成长                           │
│  ItemService    背包/合成/分解                           │
│  PartnerService 伙伴/宠物                                │
│  TaskService    任务                                     │
│  ActivityService 活动/签到/基金                          │
│  BattleService  战斗（阶段2）                            │
│  规则：一个功能域一个类，互相不直接依赖                   │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Repository 数据层                                       │
│  LocalData      内存态（唯一数据源）                     │
│  SaveProvider   存档抽象（本地/云端可换）                │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Config 配置层（复用现有，不新建）                       │
│  CFG_Item / CFG_Skill / CFG_Monster …                    │
└─────────────────────────────────────────────────────────┘
```

### 2.2 关键：LocalData 与 Manager 是两套东西，别混

上一版没说清这点，是缺陷。实际应该这样（已用代码验证）：

```
LocalData（模拟「服务端数据库」——权威数据，唯一存档对象）
      ↓
  Service 读写它，算出结果
      ↓
  构造推送对象 SyncUserBasePush{...}
      ↓
  JEvent.defaultEvent.Post(obj)
      ↓
ProtoC.Sever_SyncUserBasePush（**现成的，一行不用改**）
      ↓ 逐个字段赋值
RoleM / BagM / PartnerM / SkillM / TaskM（「客户端数据镜像」）
      ↓
       UI
```

**代码证据**：`ProtoC.cs:940 Sever_SyncUserBasePush()` 里就是
`RoleM.Instance.Coin = data.Coin; RoleM.Instance.Level = data.Level; …`，
而 `RoleM.Level` 是 `{ get; set; }` 可写。

**为什么值得这么绕**（比直接改 Manager 多约 30–50% 代码量）：

| 收益 | 说明 |
|---|---|
| ProtoC + 128 个 UI **零改动** | 它们只认推送，不关心数据从哪来 |
| **可回退** | 把 LocalServer 换回真网络，客户端代码不用动 |
| **存档边界清晰** | 只序列化 LocalData（服务端 DB），Manager 是派生数据不用存 |
| 数据流向单向 | 排查问题只需看一个方向 |

**代价**：多写一层"构造推送"的代码。对要上 TapTap、将来可能加联网的项目，这笔账是划算的。

### 2.3 推送单独一条线

推送**不进 Service**，也不进 LocalServer，由独立的调度器驱动：

```
LocalPusher（推送调度）
   ├─ OnLogin()     登录后一次性推送（UserBase/Stats/PartnerSlot/SkillSlot/Buff）
   └─ Update(dt)    定时推送（HomeAutoEncounter 遇怪、Buff 到期、CD 刷新）
        ↓
   JEvent.defaultEvent.Post(obj)   → ProtoC.Sever_*Push 自动接收
```

> 机制已验证：`ProtoMap` 有 53 条 `S2C_*`，`ProtoC` 都有对应的 `Sever_*Push`，直接 Post 对象即可，不用走 ProtoMap。

### 2.4 目录结构

```
HotUpdateScripts/LocalNet/
├── LocalServer.cs            # 路由（薄）
├── LocalHttpRouter.cs        # HTTP 路由（薄）
├── LocalBootstrap.cs          # 装配：注册路由 → 绑定 Service
├── Push/
│   └── LocalPusher.cs         # 推送调度
├── Services/
│   ├── PlayerService.cs
│   ├── ItemService.cs
│   ├── PartnerService.cs
│   ├── TaskService.cs
│   ├── ActivityService.cs
│   └── BattleService.cs       # 阶段2
├── Data/
│   ├── LocalData.cs
│   └── SaveProvider.cs        # 阶段4
└── Protocol/
    ├── TcpHandlers.cs         # CmdId → Service 的映射表
    └── HttpHandlers.cs        # URL → Service 的映射表
```

### 2.5 三条硬约束（防止结构腐化）

| # | 约束 | 违反后果 |
|---|---|---|
| 1 | `LocalServer` / `LocalHttpRouter` 里**不允许出现业务计算**，只有 `case → service.Call()` | 上帝类，改一处崩一片 |
| 2 | Service 之间**允许单向依赖，禁止循环依赖** | 循环依赖，编译不过 |
| 3 | 所有响应对象在 Service 里构造完再返回，**Adapter 不碰数据结构** | 结构散落，难改 |

> 约束 2 原本写的是"互不引用"，不现实 —— 这个游戏数据高度耦合
> （角色↔装备↔伙伴↔战斗），硬性解耦会逼出一堆无意义的转发层。
> 正确规则是：**`BattleService` 可以读 `PlayerService`/`PartnerService`，反向不行。**

## 3. 两个「现在不必定死、但要知道」的不确定项

### 3.1 战斗逻辑放热更层还是 AOT

IAA 那份文档里我倾向"AOT"，这里修正为：**先放热更层，阶段 2 做完实测再定**。

原因是查代码后发现的：服务端战斗并不是"每帧跑"——
`processHP` / `processBuff` / `processAI` 都是**定时 tick 驱动**（几十到几百毫秒一次），
不是每帧。ILRuntime 跑低频 tick 的压力远小于每帧逻辑。

**处置**：
1. 阶段 2 先写在 `HotUpdateScripts/LocalNet/Services/BattleService.cs`
2. 做完后用真实战斗实测 WebGL 帧率
3. 不达标再把 `BattleService` + 寻路迁到 `Assets/Scripts/`（AOT），此时边界已经清楚，迁移成本可控

> 好处：不因为一个未验证的性能担忧，提前付出"改代码必须重编 Unity"的代价。

### 3.2 4 张缺失配置表要不要现在就补

**不着急**。`Robot` / `ItemGroup` / `LevelGift` / `RandomCreat` 都是**特定玩法才用到**的表：
- `Robot` → 回合制玩法（阶段 D）
- `ItemGroup` → 掉落结算（阶段 2 战斗）
- `LevelGift` / `RandomCreat` → 边缘功能

按需补，不要提前全部导出。

## 4. 现有代码怎么迁移

当前 6 条协议 + 2 个 HTTP 都在 `LocalServer` / `LocalHttpRouter` 里，改造成本很低：

| 现有 | 迁到 |
|---|---|
| `LoginLocalHandler.OnLogin` | `PlayerService.Login()` |
| `BasicLocalHandlers.OnPartnerList` | `PartnerService.GetList()` |
| `BasicLocalHandlers.OnGetBag` | `ItemService.GetBag()` |
| `BasicLocalHandlers.OnInstanceInfo` | `PlayerService.GetInstanceInfo()` |
| `BasicLocalHandlers.OnDailyMapInfo` | `PlayerService.GetDailyMap()` |
| `BasicLocalHandlers.OnPvpInfo` | 空实现即可（多人内容要删） |
| `LocalHttpRouter.BuildLoginResponse` | `PlayerService.BuildLoginResponse()` |

`LocalServer` 最终只剩一张路由表。

## 5. 建议的执行顺序

| 步 | 内容 | 说明 |
|---|---|---|
| 1 | **先搭骨架**：建 `Services/` 目录 + 6 个空 Service + 迁移现有 6 条协议 | 不改行为，只改结构，一次编译就能验证 |
| 2 | 补登录主动推送（`LocalPusher.OnLogin`） | 界面数据才有值 |
| 3 | 补 8 个主城 HTTP（`ActivityService` / `ItemService`） | 邮件/商店/活动/签到可打开 |
| 4 | 补 4 张缺失配置表（Robot / ItemGroup / LevelGift / RandomCreat） | 从服务端 xlsx 导出 |
| 5 | **字段级配置审计**（为阶段 2 做准备） | 对着 `map_object.go` 逐字段核对 |
| 6 | 阶段 2：战斗核心移植 → `BattleService` | |

**第 1 步必须先做**。现在只有 6 条协议，重构几乎无痛；等堆到 50 条再改，就是大工程。
