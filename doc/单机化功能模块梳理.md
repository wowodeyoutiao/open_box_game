# 单机化功能模块梳理

> 时间：2026-10-24
> 范围：`game_machao` 客户端（Unity 2022.3.14f1c1 / HotUpdateScripts 热更层）+ Go 服务端
> 前提：版权已确认无问题；**多人内容全部去掉，只保留单人玩法**
> 目的：把现有功能摊开看清，作为删减与改造的作业底图

---

## 0. 一句话结论

**单人核心（战斗 / 养成 / 放置 / 活动）约占服务端逻辑的 70%，可原样保留；真正要砍的多人部分约 15–20%，但它们是"嵌在大文件里的方法"而不是独立文件，所以删减方式是「按方法摘除 + 清引用」，不是「删文件」。**

## 7. 关键发现与风险

| # | 发现 | 影响 |
|---|---|---|
| 1 | 回合制对手是机器人，不是真人 | 🟢 该玩法可保留，改造量小 |
| 2 | 世界 Boss 是全服共享伤害结构 | 🔴 无法单机化，必删 |
| 3 | 聊天/排行是**嵌入式方法**，非独立文件 | 🟡 删减成本高于预期，需逐方法摘 |
| 4 | 牌桌/房间/匹配框架被回合制复用 | 🟡 不能整体删除，否则连带打挂回合制 |
| 5 | 支付通道本身是空的（`mer_id` 占位、无支付 SDK） | 🟢 付费功能改广告是**换皮而非拆骨**，成本低 |
| 6 | 但**付费文案**仍遍布 UI | 🔴 出现「充值/支付/¥」字样即可能被判含内购，必须全量改写 |
| 7 | `UITurnBox`/`UIRouletteWheel` 涉概率 | 🟡 合规敏感，需公示概率且不与真实货币挂钩 |
| 8 | 广告 SDK 尚未接入 | 🟡 需接 TapTap 的 Dirichlet 广告联盟，是新工作量 |

## 8. 建议的删减批次

| 批次 | 内容 | 风险 | 说明 |
|---|---|---|---|
| **批次 1** | **付费功能广告化**：`UIShop`/`UIFirstPay`/`UIVIP`/`UIPrivilegeCard`/`UITrialFund`/`UIGiftBag` 换广告驱动 + 文案全量改写，`UIPayBind*` 删除 | 中 | **优先做**，它是合规红线，且只动展示层与触发点，不碰玩法逻辑 |
| **批次 2** | 公会全删（12 UI + 17 协议 + `guild_manager.go`） | 低 | 独立文件，边界清晰 |
| **批次 3** | 聊天 + 排行榜 + 观战 + 选服/手机登录/实名 | 中 | 嵌入式方法，需清引用 |
| **批次 4** | 真人 PVP / GVG / 世界 Boss | 中 | 注意保留回合制所需的 desk/room 框架 |
| **批次 5** | 主城 UI 重排 + 底部功能栏改版 | 中 | 依赖前 4 批完成 |

## 10. 付费功能 → 广告驱动 改造规格

> 决策依据：后期用广告承接原付费点，**功能不删、只换引擎**。
> 有利前提：**当前代码里没有任何真实支付 SDK**（无 WxPay / IAP / unifiedorder 实现），服务端 `mer_id` 也是占位符 —— 相当于"支付通道本来就没接"，所以这次是**换皮，不是拆骨**。

### 10.1 合规判定原则

| 判断 | 结论 |
|---|---|
| 「看广告 → 获得特权/奖励」 | ✅ IAA 变现，不属于内购 |
| 「有付费 UI 但背后是广告」 | ⚠️ **功能可以留，但文案必须改**，否则审核按内购处理 |
| 「出现充值/支付/¥/真实货币字样」 | 🔴 直接触发内购判定，免版号资格失效 |
| 「接真实支付通道（微信/iOS IAP）」 | 🔴 绝对禁止 |

**一句话：留功能、换触发、洗文案、不碰支付。**

### 10.2 付费系统层映射（9 个 UI）

| 原功能 | 现有机制（已核实） | 广告化方案 | 落点 |
|---|---|---|---|
| `UIFirstPay` 首充 | 充值一笔得大礼 | 「首次看广告领开服大礼」，每日限 1 次 | 换触发点，配置保留 |
| `UIVIP`（15 级） | `NeedEXP` 累计升级 | 看广告 **+EXP**（设每日上限），VIP 特权照旧 | `vip.json` 的 `NeedEXP` 保留，加日限配置 |
| `UIPrivilegeCard` 周卡/月卡 | 付费买 `Duration` 天 | 每日看广告领 `Dailyaward`，累计达标解锁特权 | `privilege.json` 字段可直接复用 |
| `UITrialFund` 试用基金 | 付费解锁 → 达成返还 | 看广告解锁，达成条件返还钻石 | 换解锁触发 |
| `UIGiftBag` 礼包 | 付费购买 | 低档：看广告免费领；高档：游戏币购买 | 按档位分流 |
| `UIShop` 商店 | 钻石充值 | 改「看广告领钻石」+ 游戏币兑换商店 | 裁剪 `store` 配置 |

### 10.6 🔴 一个必须提前想清楚的商业问题

原游戏是「花钱买数值」，改成「看广告买数值」后：

- **单位用户收益会大幅下降**（激励视频 eCPM 通常只有充值 ARPU 的几分之一到十几分之一）
- 原充值档位的数值供给，需要重新映射成「广告次数 × 单次奖励 + 等待时间」
- 数值曲线要重调：广告次数有上限，奖励给太少玩家会流失，给太多广告价值被稀释

**建议**：付费广告化之前，先把「原付费档位 → 目标广告观看次数 → 对应奖励量」这张映射表列出来，再动代码。这张表决定留存的健康度，比技术实现更关键。

### 10.7 落地顺序建议

1. 先接 Dirichlet 广告 SDK，跑通「播一次激励视频 → 拿到回调 → 发一次奖励」的闭环（**独立验证，不掺业务**）
2. 再挑一个最简单的付费点（建议 `UIHPAdd` 体力补充）做首个广告化样板
3. 样板跑通后，按 10.2 / 10.3 的表批量铺开
4. 最后做 10.4 的文案全量清洗 + 概率公示 + 支付痕迹拆除
5. 上线前做一次「全量关键词扫描」：整个工程搜不到 `充值|支付|¥` 才算过
