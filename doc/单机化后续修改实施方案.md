# 单机化后续修改实施方案

> 评估日期：2026-10-25  
> 输入依据：《单机化整体评估与开发规划》、当前客户端本地服务代码、配置表、Prefab 与 Go 原服逻辑  
> 本文性质：后续修改的方案评估与实施边界，不代表这些代码已修改  
> 结论：方向成立，可以按本文分批实施；但必须先修正初始化、严格离线和存档顺序，不能继续以“补成功响应 + UI 自驱动画”作为主线。

---

## 0. 总体判断

### 0.1 可以继续当前架构

继续保留：

```text
UI
→ TcpC / HttpC
→ LocalServer / LocalHttpRouter（薄 Adapter）
→ 本地 Service
→ 权威数据 + 存档
→ 响应 / 推送
→ ProtoC / Manager
→ UI
```

这个方案没有明显架构性错误，真正的问题是**工程约束尚未落地**：

- 本地启动入口没有真正接上；
- 网络层的失败语义不完整；
- 本地权威数据模型和存档边界还没建立；
- 建角、装备、属性、挂机存在硬编码和双规则；
- 战斗仍为空，当前挂机只是表现闭环，不是玩法闭环。

### 0.2 后续修改要遵守三条主原则

1. **先修基础设施，再扩玩法。**  
   严格离线、请求终态、统一初始化、存档 V1 必须先于大量业务迁移。

2. **一个状态只有一个权威来源。**  
   角色进度只写 `LocalData` 领域数据；`RoleM`、`BagM` 只接收推送。UI 不能直接决定金币、掉落、战斗结果。

3. **表现可以临时兜底，但不能冒充规则完成。**  
   大厅可以先修朝向、动作、特效，但伤害、死亡、奖励必须由 `HomeAFKService` / `BattleService` 给出。

### 0.3 相比上一版规划，需要调整的四个顺序

| 原计划倾向 | 本次评估建议 | 原因 |
|---|---|---|
| 先补大厅表现，再逐步存档 | 表现可并行做最小修复，但**存档 V1 与统一建角必须更早** | 现在每次进入游戏都会重置数据，继续加系统会反复返工 |
| 先补更多协议覆盖 | 先建立“未实现/假成功/真实现”终态 | 当前协议覆盖数量不能代表玩法完成度 |
| 配置表基本齐全，按需补四张 | `maintrigger` 实际未导出到客户端，挂机奖励当前无数据基础 | 现有 `guidance.json` 是新手引导，不是挂机触发表 |
| 挂机走 UI 定时器也行 | 短期保留表现驱动，但收益规则必须迁入本地 Service | 否则 UI 关闭、异步竞态和重启都会影响奖励正确性 |

## 1. 本轮新增核实结果

### 1.1 `LocalBootstrap.Init()` 没有实际启动点

`LocalBootstrap` 文件已经存在，但在 `HotUpdateScripts` 中没有找到调用 `LocalBootstrap.Init()` 的位置。

当前实际初始化顺序更接近：

```text
UILogin 加载配置
→ HTTP 登录
→ PlayerService.BuildLoginResponse
→ LocalData.EnsureInit
→ LocalData.Reset
→ 进入选角
→ TCP C2S_Login
→ LocalServer.TryHandle
→ LocalServer.Init
```

这带来三个问题：

- 存档没有机会在选择角色之前加载；
- “默认角色”会先被创建，真实存档可能被覆盖；
- `LocalBootstrap` 作为装配入口目前是死代码，不能承担初始化职责。

**修改建议**：在 `UILogin` 完成配置表加载后、发起登录前调用一次幂等的 `LocalBootstrap.Init()`。不要在 `LocalData.EnsureInit()` 里偷偷加载存档，否则数据层职责会继续混乱。

### 1.2 当前有两个互不关联的单机开关

- `GameM.IsLocalMode`：控制区服列表是否走本地；
- `LocalServer.Enabled`：控制 TCP/HTTP 是否走本地应答。

这两者可以分别被修改，存在“界面以为是本地服，但网络层已经切真服”或相反的配置漂移。

**修改建议**：统一为单一 `LocalRuntimeMode`：

```text
Remote          仅开发对照，走真实网络
LocalCompare    本地优先，未命中时允许真网并抓包
LocalStrict     发布单机模式，禁止任何真网回退
```

`GameM.IsLocalMode` 和现有 `LocalServer.Enabled` 只作为过渡兼容字段，最终由统一模式派生。

### 1.3 HTTP 未命中时仍会走真网络

`HttpRequestHelper.SendPost<T>` 的两个重载都有同样行为：

```text
Factory 未命中
→ JSON 路由未命中
→ 检查网络可达
→ 真实网络请求
```

因此在当前代码里，`LocalServer.Enabled = true` 仍不等于“离线”。

**修改建议**：

- `LocalStrict` 模式下，未命中本地路由不能调用 `NetworkHelper.SendPost`；
- 必须走失败回调 `NoFun` 或统一的“未开放”提示，并记录 URL；
- 抓包能力只允许在 `LocalCompare` 模式启用；
- 发布构建不能因为连接不到服务器而卡在 loading。

### 1.4 TCP 未实现协议会被吞掉，调用方没有终态

`LocalServer.TryHandle()` 的行为是：

```text
已注册 → 执行 Handler → 返回 true
未注册 → 记录 MissingCmds → 返回 true，response = null
异常   → 记录日志 → 返回 true，response 可能为 null
```

调用方只看到“已接管”，却收不到成功、失败或“不支持”的明确结果。

**修改建议**：把 `bool TryHandle` 改为带结果的状态：

```csharp
public enum LocalHandleOutcome
{
    Handled,
    NotImplemented,
    Failed
}

public sealed class LocalHandleResult
{
    public LocalHandleOutcome Outcome;
    public object Response;
    public string Error;
}
```

严格离线时：

- `NotImplemented`：不发送网络请求；记录协议；关闭 loading；提示功能未开放；
- `Failed`：记录错误；走明确失败路径；
- `Handled + Response == null`：视为实现错误，不能当作成功。

### 1.5 当前“假成功”动作必须退出主流程

`GamePlayLocalHandlers` 对以下协议统一返回 `Code = 0`：

- 角色升级；
- 宝箱设置、升级、快速升级；
- 伙伴上阵、合成、分解、重铸、替换、休息、升星；
- 宠物升级；
- 一键装备；
- 战斗奖励。

这些操作会在界面上表现为成功，但没有任何权威数据变化。

**修改建议**：不要一次性全部实现，但必须先把它们从“成功”降级为明确未实现，再按依赖逐个迁入 Service。当前协议覆盖数字应从完成度中剔除。

### 1.6 建角与默认角色的初始化规则不一致

当前有两条创建路径：

- `LocalData.Reset()`：创建“本地勇者”，并直接配置初始背包和装备；
- `PlayerService.BuildCreateCharResponse()`：只创建名字、职业、性别、等级和体力。

因此，玩家自己新建的角色很可能没有装备，而开发默认角色有装备。这正好解释了“默认有的看、新建角色可能没有”的现象。

**修改建议**：新增唯一的新角色工厂，所有路径都调用它：

```csharp
NewRoleFactory.Create(long uid, string name, int job, int sex);
```

`LocalData.Reset()` 不再自己拼一套初始装备；`BuildCreateCharResponse()` 也不再手写另一套最小字段。

### 1.7 现有 101～106 初始装备只适用于战士

从 `item.json` 校验得到：

| 职业 | 一级基础装备 ID | 部位 |
|---|---|---|
| 战士 | 101～112 | 武器、衣服、头盔、项链、双戒、双手镯、腰带、鞋子、护腿、饰品 |
| 法师 | 1913～1924 | 同上 12 个部位 |
| 祭祀 | 3725～3736 | 同上 12 个部位 |

当前 `LocalData` 只写死 101～106，且这些物品的 `Occupylimit = 1`，即仅限战士。若直接把当前初始化逻辑复用到新建法师或祭祀，会发放该职业不能使用的装备。

**修改建议**：建立按职业声明的新手装备配置，至少包含 12 个基础部位。当前阶段可以先使用显式白名单表，待配置管线稳定后再迁入 JSON。

还需处理两个细节：

- `ItemInfo.Equip = new EquipInfo()` 中没有属性；UI 中“是否最佳装备”等判断会读取实例 `Equip.Attributes`；
- 固定 `Uid = 900000x` 在不同角色间会重复。

解决方向：

- 属性计算以 `CFG_Item` 基础配置为兜底，或初始化时写入规范化的实例属性；
- 新增账号级 `NextItemUid`，所有发装备必须走统一 UID 分配器。

### 1.8 原服创角送装备在当前配置下并不可靠

原服 `CreateRoleSendProps()` 从 `global.GlobalCfg.CreatAward` 读取道具并生成“登录送装备”邮件。

但在当前仓库中：

- Go 代码声明了 `CreatAward` 结构；
- 没有找到 `config.xml` 中的 `<Creataward>` 节点；
- 因此按当前配置，该邮件附件可能为空。

**结论**：不能把“原服邮件送装备”当作完整可靠的产品规则。单机版应明确设计自己的新手装备来源。

### 1.9 存档仍只有接口，没有实现

`LocalFileSaveProvider` 的四个方法都返回 `false` 或空操作。更关键的是，当前 `LocalData` 直接使用协议类型：

- `Bag`
- `ItemInfo`
- `PartnerInfo`
- `EquipSlot`

如果直接对 `LocalData` 使用 `JsonUtility`，会遇到：

- `Dictionary<EquipSlot, ItemInfo>` 不被支持；
- 热更层程序集、枚举、嵌套类和空集合的行为不稳定；
- 协议结构变化会影响旧存档；
- `LocalRole.Clone()` 没有复制 `BagData`、`Partners`、`Equips`，深拷贝本身不完整。

**修改建议**：不要直接序列化 `LocalData`。新增独立的存档 DTO，与协议对象解耦。存档只保存进度，不保存客户端 Manager、临时计时器、UI 引用和缓存属性。

### 1.10 挂机配置被写死且与现有配置不一致

`config.xml` 中当前配置为：

```xml
<onlinebattle basetime="7200" triggertime="10" limittime="1"/>
```

但当前代码使用：

- `LocalPusher.PushUserBase()`：`HomeAFK = 3600`；
- `UIHall.StartLocalHomeEncounter()`：固定 6 秒一次遇怪。

正确语义应是：

- `basetime`：基础在线挂机时长；
- `triggertime`：事件触发间隔；
- `limittime`：点击间隔；
- 服务端的 `HomeAFK` 为“基础时长 + 活力加成 - 已用时间”的剩余值，不是固定常量。

**修改建议**：把挂机剩余时间、已用活力时间、下次事件时间做成角色持久化状态，所有数值来自配置，不在 UI 和 Pusher 各自写常量。

### 1.11 挂机奖励缺少客户端配置基础

服务端使用 `maintrigger.xlsx` 驱动挂机随机事件：

- 普通奖励；
- 怪物；
- 怪物掉落；
- 按等级区间和权重抽取。

当前客户端 `TextAssets` 中没有 `maintrigger.json`。现有 `guidance.json` 是新手引导文本，字段为 `ID / type / describe`，不能替代 `maintrigger`。

**结论**：挂机收益不能仅靠现有客户端表实现。实施前必须从服务端导出 `maintrigger`，怪物掉落还需要 `dropcontrol`/`ItemGroup` 对应数据。

### 1.12 大厅表现问题的当前事实

- 怪物使用 `moester`，骨架来自 BOSS `Boss_jz1`；
- 当前资源是正面朝向，简单设置 `localScale.x = -1` 不能解决左右朝向；
- 怪物 Prefab 默认动画是循环 `stand`，当前代码没有触发它攻击；
- 特效在异步刷怪完成之前触发，因此首轮常回退到主角位置；
- `eff_other_ui_boom` 有真实粒子，但根节点原始缩放为 `150`，当前代码覆盖为 `1`，可见性与大小必须实机确认；
- 当前特效不是命中事件驱动，而是一次遇怪调用一次。

**评估结论**：

- 朝向若必须左右分明，最终依赖美术资源/骨骼朝向修正；
- 怪物攻击和玩家特效可以做最小修复，但完整正确性要等战斗事件；
- 不应继续在 `UIHall` 内增加更多计时器、状态字段和奖励逻辑。

### 1.13 当前没有自动化测试基线

在 `HotUpdateScripts` 下没有找到测试目录，也没有本地服务层的测试程序集。当前主要靠 Console 日志验证，这正是“状态看似跑通、细节反复回退”的原因之一。

**修改建议**：不要求一开始就建立完整的 Unity Test Framework 工程，但至少要有：

- 一个只依赖纯 C# 的领域自检入口；
- 存档读写的往返测试；
- 新角色初始化的职业矩阵测试；
- 装备穿脱和属性重算测试；
- 挂机随机种子与奖励幂等测试。

领域计算尽量不依赖 `MonoBehaviour`，否则后续测试成本会继续上升。

## 2. 目标修改架构

### 2.1 目标数据流

```text
操作请求
→ Adapter 返回 LocalHandleResult / LocalHttpResult
→ Service 校验并执行领域规则
→ 一次性修改权威 LocalData
→ 标记存档脏数据
→ 生成响应 + 推送
→ ProtoC 更新 Manager
→ UI 刷新

任何失败：
→ 返回明确失败终态
→ 不修改权威数据
→ 不发送成功推送
→ 记录诊断信息
```

### 2.2 建议的新增/调整模块

以下是建议名称，不代表必须按此命名；关键是职责边界。

| 模块 | 职责 | 实施优先级 |
|---|---|---|
| `LocalRuntimeMode` | 统一运行模式、严格离线、抓包开关 | P0 |
| `LocalHandleResult` / `LocalHttpResult` | 统一成功、未实现、失败、异常语义 | P0 |
| `LocalBootstrap` | 配置加载后加载存档、初始化路由、启动服务 | P0 |
| `NewRoleFactory` | 唯一的新角色创建入口 | P0 |
| `StarterLoadoutConfig` | 按职业给出新手装备、货币、技能初始状态 | P0 |
| `SaveDocument` + `SaveSerializer` | 与协议对象解耦的版本化存档 | P0 |
| `SaveCoordinator` | 脏标记、节流保存、退出/暂停保存、错误恢复 | P0 |
| `RoleStatService` | 基础属性、装备加成、战力统一计算 | P0 |
| `HomeAFKService` | 挂机时间、遇怪、奖励、满包、离线收益 | P0/P1 |
| `HallAFKPresenter` | 消费挂机事件，控制怪物、动画、特效 | P0/P1 |
| `BattleService` | 固定 tick、战斗单位、技能、死亡、结算 | P0 最小/P1 完整 |
| `LocalDiagnostics` | 未实现协议、失败路由、假成功清单导出 | P0 |

### 2.3 不建议现在做的重构

以下改动收益不高或风险偏大，不应混进第一批：

- 全量替换 `LocalData` 中的所有协议类型为自定义领域类型；
- 为所有 Service 引入接口、依赖注入容器和完整 Repository 框架；
- 把所有 105 个推送一次性重写；
- 在战斗规则尚未稳定时重做全部 UI；
- 把 `UIHall` 整体推倒重建；
- 继续为所有未实现协议补空响应来追求“覆盖率”。

## 3. 修改工作包

### CP-00：建立基线与诊断台账

**目标**：先让问题可见，避免“界面打开了但不知道数据有没有变”。

**涉及文件**

- 新增 `LocalDiagnostics`；
- 调整 `LocalServer`、`LocalHttpRouter` 记录未实现与异常；
- 项目文档维护协议/功能台账。

**具体工作**

1. 为每条上行协议和 HTTP 接口标记：
   - `未接`
   - `兼容桩`
   - `假成功`
   - `真实规则`
   - `已存档`
   - `已验收`
2. 运行时支持导出：
   - `MissingCmds`
   - 未命中 HTTP URL
   - Handler 异常
   - 假成功协议列表
3. 建立最小领域自检入口。

**验收**

- 能导出一份当前缺失/假成功清单；
- 每个已开放按钮都能找到对应台账项；
- 新接业务不能以“返回 Code=0”标记为完成。

**复杂度**：S  
**风险**：低  
**建议批次**：第 1 批

---

### CP-01：统一运行模式与严格离线

**目标**：保证发布版绝不回退真实网络，并让所有请求有明确终态。

**涉及文件**

- `GameM.cs`
- `LocalServer.cs`
- `LocalHttpRouter.cs`
- `TCPClientMgr.cs`
- `HttpRequestHelper.cs`
- `LocalBootstrap.cs`
- `HttpC.cs`
- `UISelectRole.cs`

**具体工作**

1. 建立 `LocalRuntimeMode`：
   - `Remote`
   - `LocalCompare`
   - `LocalStrict`
2. `LocalServer.Enabled` 由运行时模式派生，避免多开关漂移。
3. `TryHandle` 返回 `LocalHandleResult`，不再用 `bool + null response`。
4. TCP 未实现：
   - 严格模式下不发真网；
   - 记录协议号；
   - 关闭等待状态；
   - 给出统一提示或由功能入口禁止触发。
5. HTTP 未命中：
   - `LocalStrict` 直接失败；
   - `LocalCompare` 才允许 `NetworkHelper.SendPost` 与抓包；
   - Factory 抛异常不能降级真网，直接走失败。
6. `HttpC.OnLoginSever` 不再直接绕过统一模式判断。
7. 未实现的非关键入口暂时隐藏：
   - 伙伴培养；
   - 宠物升级；
   - 宝箱升级；
   - 一键装备；
   - 战斗奖励。

**不要做**

- 不要为未实现协议根据猜测构造响应；
- 不要在严格模式下静默把 `null` 当成功。

**验收**

1. 断网冷启动，不出现任何真实服务器连接尝试；
2. 点击未实现入口不会永久 loading；
3. Console 能列出未实现协议和未命中 URL；
4. `LocalCompare` 抓包仍可用于开发期对拍；
5. 发布构建没有 `http_capture.log` 写入行为。

**复杂度**：M  
**风险**：中，触及全部网络入口，但当前入口数量少，适合现在做  
**建议批次**：第 1 批

### CP-02：启动链、存档 V1 与数据边界

**目标**：让角色进度可以可靠保存、加载和迁移，避免后续系统建立在不稳定数据上。

**涉及文件**

- `LocalBootstrap.cs`
- `UILogin.cs`
- `LocalData.cs`
- `SaveProvider.cs`
- 新增 `SaveDocument` / `SaveSerializer` / `SaveCoordinator`

**关键设计**

存档对象建议独立定义，示意：

```csharp
public sealed class SaveDocument
{
    public int SchemaVersion;
    public long SavedAtUnix;
    public long NextRoleUid;
    public long NextItemUid;
    public long CurrentRoleUid;
    public List<RoleSaveV1> Roles;
}

public sealed class RoleSaveV1
{
    public long Uid;
    public string Name;
    public int Job;
    public int Sex;
    public int Level;
    public long Exp;
    public long Coin;
    public long Diamanta;
    public long Coupon;
    public long Soul;
    public long Energy;
    public int CurHp;
    public long HomeAFKUsedSec;
    public long HomeAFKAnchorUnix;
    public long LastSeenUnix;
    public List<ItemSaveV1> Bag;
    public List<EquipSaveV1> Equips;
    // 任务、伙伴等按模块逐步加入
}
```

字段只做方向示意，正式实现要按现有领域字段确认。

**修改重点**

1. `LocalBootstrap.Init()` 在配置表加载完成后调用：
   - 初始化运行模式；
   - 尝试加载存档；
   - 初始化路由；
   - 初始化全局 tick 驱动。
2. `LoadResult` 必须区分：
   - `NoSave`
   - `Loaded`
   - `Corrupt`
   - `VersionUnsupported`
3. 损坏存档不能静默覆盖为新档，要保留原文件或备份并提示。
4. 保存策略：
   - 关键操作后标脏；
   - 短时间合并写入；
   - 应用暂停/退出时强制保存；
   - 定时自动保存；
   - WebGL 不使用仅依赖 `OnApplicationQuit` 的策略。
5. 写入采用临时文件 + 备份替换，避免写一半损坏。
6. `LocalData.EnsureInit()` 只保证容器就绪，不再偷偷 `Reset()` 成默认角色。
7. `LocalRole.Clone()` 要么补全深拷贝，要么删除无用接口，不能保留错误语义。

**首次启动的产品选择**

有两种可行方案：

- **推荐：无存档 → 角色列表为空 → 进入建角流程。** 玩家能选职业，所有角色走同一初始化规则。
- 开发便利方案：自动创建本地勇者。但它必须复用 `NewRoleFactory`，不能再用 `Reset()` 单独手写一套。

正式产品建议采用第一种；开发期可保留一个显式调试开关创建默认角色。

**验收**

1. 首次启动进入建角，或通过显式调试开关创建角色；
2. 建角 → 进大厅 → 强退 → 重启，角色和货币不丢失；
3. 背包、装备、等级、当前血量正确恢复；
4. 存档损坏能保留原档并提示，不导致无法启动；
5. 多角色不串档；
6. Editor 与目标 WebGL 平台都验证持久化。

**复杂度**：L  
**风险**：中高，涉及数据结构和启动顺序  
**建议批次**：第 1 批，必须先于大量玩法接入

## 5. 关键设计决策

### 5.1 存档格式

**建议**：采用显式 DTO + 版本化 JSON。  
**不建议**：直接 `JsonUtility.ToJson(LocalData)` 或序列化 Proto 类型。

理由：

- `JsonUtility` 不支持字典；
- 热更程序集和嵌套结构容易踩坑；
- 后续字段变动难以迁移；
- 协议不是存档契约。

如果后续存档体量变大，可再切换二进制；V1 先保证可读和可迁移。

### 5.2 角色属性是否入档

**建议**：

- 基础属性由配置和等级计算；
- 装备属性由装备配置和实例数据计算；
- `Attack / Defense / MaxHp / Combat` 作为运行时缓存，不作为独立真相；
- 只持久化 `CurHp`、等级、经验、装备、任务等进度。

这样修改公式或配置后，旧档能重新计算出新属性，而不是被旧缓存锁死。

### 5.3 新手装备

**建议**：直接穿完整本职业 12 件基础装备，不再同时发相同创角邮件。

需要 Boss 最终确认的点：

- 是否保留“装备穿脱教学”；
- 是否只穿部分、部分放背包；
- 是否需要一件“邮件领取”的仪式感。

工程上无论选择哪种，都必须走统一工厂和唯一发奖入口。

### 5.4 人物外观

**建议**：第一阶段只保证装备数据与装备槽正确。  
人物模型继续使用职业/性别 Spine，不建纸娃娃系统。

原因：

- 当前模型选择只按 `Job + Sex`；
- 没有装备外观换装映射配置；
- 纸娃娃会牵涉角色美术资源、武器挂点、动作兼容和性能，是独立项目；
- 先做装备数据不代表必须做装备外观。

### 5.5 战斗放热更还是 AOT

**建议**：继续保持 `BattleService` 在热更层，先做最小战斗并实测 WebGL。  
只有实测证明 ILRuntime 无法满足帧率或内存，才迁往 AOT。

不要因为“战斗代码多”就提前搬 AOT，否则每次调试都要重编，开发速度会显著下降。

### 5.6 服务器规则的使用方式

**建议**：

- 原服作为规则参考和结果对拍，不作为直接运行时依赖；
- 逐模块迁移，不复制 Nano/MySQL/Redis；
- 原服 TODO 项标注为“需重新设计”，不能当成已完成规则。

## 6. 风险矩阵

| 风险 | 触发点 | 影响 | 缓解措施 |
|---|---|---|---|
| 存档加载晚于默认角色创建 | `LocalData.Reset()` 仍是隐式入口 | 覆盖真实档、角色丢失 | 配置加载后先执行 Bootstrap，再开放登录 |
| 严格模式仍偷偷联网 | 两个 SendPost 重载 | 发布包依赖远端、离线失败 | 统一 Mode，单一出口，断网验收 |

| 旧文档误导排期 | 文档状态与源码不一致 | 重复返工 | 以源码和当前台账为准 |

### 41.2 升级规则：一个容易读反的判据

原服 `Player.getCombatPartnerNum()`：

```go
func (p *Player) getCombatPartnerNum() int32 {
    if p.partners == nil { return 0 }
    num := 1                          // ← 从主角本人算起
    for _, v := range p.partnerSlots {
        if v.PartnerUid > 0 { num++ }
    }
    return num
}
```

所以：**没伙伴 = 1、1 个伙伴 = 2、2 个伙伴 = 3**。

两处都依赖它：

```go
// 获得经验（ItemTypeExp）
if p.getCombatPartnerNum() == 1 {   // 只有主角，没伙伴上阵
    p.levelUp()                     // → 自动升级
}
// 手动升级（Player.levelUp）
if p.getCombatPartnerNum() == 1 {
    for p.exp >= cfg.NeedExp { ... }   // while 连升
} else {
    if p.exp < cfg.NeedExp { return false }
    ...                                 // 只升 1 级
}
```

**含义：没伙伴时经验直接喂给主角自动连升；一旦有伙伴上阵，经验只进池子，
要玩家到经验池界面手动分配。** 这就是「经验池」这个模块存在的意义。

如果读成「上阵 1 个伙伴才自动升级」，行为会完全反过来——
第一版就踩了这个坑，`level` 用例（无伙伴连续升级）直接挂掉。

实现：

```text
LevelUpService.GetCombatUnitNum(role) = 1 + 上阵伙伴数
ProcessLevelUp：战斗单位数 == 1 → while 连升，否则只升 1 级
AddExp：只有战斗单位数 == 1 才自动调 ProcessLevelUp
```

### 41.3 伙伴升级

`PartnerService` 没有单独的经验，**消耗的是主角经验**（原服 `player.exp -= cfg.NeedExp`）。

```text
LevelUpService.LevelUpPartner(role, partner)
  1) partner.Level >= maxlevel        → false
  2) partner.Level >= role.Level      → false（原服 Manager 层先拦，报"已达最大等级"）
  3) needExp = CFG_Role(partnerJob, partner.Level).NeedEXP
  4) role.Exp < needExp               → false
  5) role.Exp -= needExp; partner.Level++
```

协议 `C2S_UpgradeLevel` 的 PARTNER 分支：

```text
伙伴不存在              → Code=-2
partner.Level >= role.Level → Code=-3「伙伴等级不能超过主角等级」
升级成功                → Recalculate + PushUserBase + PushStats
```

### 43.4 踩到一个 ILRuntime 深坑：cgt 指令

**现象**：`CountBought` 第一次调用（购买记录为空）正常，第二次（有记录）抛
`NotImplementedException`。加一行 `Log.Print` 就恢复正常，删掉又崩 —— 典型的优化路径敏感。

**根因**：`ILIntepreter.Register.cs` 的 `cgt` 指令分支：

```csharp
switch (reg1->ObjectType)
{
    case ObjectTypes.Integer: ...
    case ObjectTypes.Long: ...
    case ObjectTypes.Float: ...
    case ObjectTypes.Double: ...
    default:
        throw new NotImplementedException();   // ← 崩在这里
}
```

`window <= 0`、`now - boughtAt <= window` 这类 **long 的 `>` / `<=` 比较**会编译成 `cgt`，
某个 register 的 `ObjectType` 不是数值类型时就抛异常。

**规避**（已验证有效）：

```csharp
// ❌ 会崩
if (window <= 0) return true;
return now - boughtAt <= window;

// ✅ 只用 < 和 ==，彻底绕开 cgt
if (window == 0L) return true;
long elapsed = now - boughtAt;
if (elapsed < window) return true;
if (elapsed == window) return true;
return false;
```

排查过程中的其他错误判断（记录下来避免再走弯路）：

```text
1) 以为是 List<StoreBuyRecord> 泛型问题 → 改成 List<long> 平铺，仍崩
2) 以为是 continue 跳转问题        → 改成正向 if，仍崩
3) 以为是 long 局部变量过多        → 把构造抽成独立方法，仍崩
4) 加 Log.Print 就过 → 说明是代码生成路径问题，不是数据问题
5) 最后去看 ILRuntime 源码定位到 cgt 分支
```

## 50. 一键镶嵌（2026-10-27 21:05）

### 50.1 原服实现（Player.genstoneChangeAll）

和单颗镶嵌是**两套逻辑**，不是「循环调单颗镶嵌」：

```text
1) 从背包扫 DiamondPosition 含该部位的魂石，按**堆叠数量展开**成一条条候选
   {ID: cfgId, Num: itemlevel, Key: 1}      ← Key 1 = 背包
2) 身上 4 槽整理成 old[]（空槽 {0,0}）      ← Key 2 = 身上
3) canSlot = 等级对应的开槽数
4) for i = 1..canSlot：
     topFourByField(canDell, 1, 1)  → 按 itemlevel 降序取最高一颗（**只排序取值，不删除**）
     在 old 里找第一个「等级更低」且「j < canSlot」的槽位：
        旧槽非空 → 扣新宝石 → 旧宝石退回背包 → 旧宝石**丢回候选池**
        旧槽空   → 直接扣新宝石
     写入槽位 → 更新 old[j] → break（一轮只处理一个槽位）
5) 回包 = 4 个槽位的最终值
```

三个照抄原服的点：

```text
① 只换「等级更高」的，同级不换（newInfo.Num > olditem.Num）
② 每轮只处理一个槽位就 break，下一轮重新取最高候选（所以同一个槽位可能被连续升级多次）
③ 原服有一行 `if int32(olditem.Num) >= newInfo.ID { continue }`：
```

### 54.3 三个坑（都值得记）

**① `MapMark` 字段接不了 —— LitJson + ILRuntime 的 null 问题**

`battle.json` 里 `MapMark` 取值是 `1.0` 或 `null`。三种写法全部失败：

```text

public decimal? MapMark;   → JsonException: Can't assign '1' (Double) to Nullable<Decimal>

                             之后 (int)cfg.MapMark 在 ILRuntime 的 Decimal_Binding 里 NRE
```

**③ 怪物会追着玩家跑，测试不能拿静态坐标走位**

`enter.TableInfo.MonsterList[i].Location` 是**进入时**的坐标，怪物追人之后早就变了，

### 55.2 属性结算（RoleStatService.AddPets）

严格照抄原服 `refreshStats` 的宠物段：

```text
petStatus := {}                                  // 只装原值 + 百分比
if p.pet[0].PetCfgId != 0 {
    StarAttribute[Star]                          → petStatus（百分比属性）
    RoleCfg(Pet, Level).BassProperty × 品质系数    → petStatus（数值属性）
        品质系数 = GetpetQualityRate(Quality)；为 0 或 PetKind.key==2（经验宝宝）时取 1
    newpetStatus = 攻/魔攻/物防/魔防/生命 各自 × (1 + 自身百分比/10000)
    **只把这 5 个属性**并进 p.stats
}
```

三个容易做错的点：

```text
① 只有 0 号槽（上阵）的宠物给属性，包裹里的完全不算；
② 星级属性是百分比，和等级基础属性进的是**同一个桶**，最后只对那 5 个属性做放大；
③ 放大完只并入 5 个属性，百分比本身不能进总属性（否则跟装备百分比叠成双倍）。
```

两个实现细节：

```text
· 位置很关键：AddPets 必须在 AddGemstones **之前** —— 原服是先加宠物、再算魂石的
  「生命百分比尾数」，也就是宠物血要算进 gemHealthPercent 的基数里；
· 舍入必须用 Math.Round(x, MidpointRounding.AwayFromZero)：原服是 Go 的 math.Round
  （.5 远离 0），C# 默认是银行家舍入，91 × 3.5 = 318.5 会差 1 点变成 318 而不是 319。
```

## 60. ②-B 伙伴合成 / 分解 / 洗练（2026-10-28）

`C2S_PartnerCompose` / `C2S_PartnerDisassemble` / `C2S_PartnerReforge` 三个
`RegUnsupported` 全部换成真实现，对齐 `player.go` 的 `partnerCompose` /
`partnerDisassemble` / `partnerReforge`。

### 60.1 先纠正一个语义误读（重要）

原服这两个名字都**不是「把伙伴删掉」**：

| 接口 | 实际语义 |
|---|---|
| `partnerDisassemble`（分解） | 校验 Quality/Starlevel 门槛后，把伙伴**重置回 1 级 0 星**，退还星级材料 + 升级经验 |
| `partnerReforge`（洗练/重铸） | 免费退 `Forge.Free.Rate%`（当前 70），付费扣品质对应道具后退全额，同样**重置回 1 级 0 星** |
| `partnerCompose`（合成） | 消耗 `ChipNum` 碎片换整卡；已拥有同配置则直接报错，不重复给 |

所以「分解」不会让玩家失去伙伴，只是清空养成投入。

### 60.2 三条链路的关键差异

```text
碎片处理   分解：星级材料里 Type=7（伙伴碎片）按 Rate% 折算成通用碎片 id 95，
                 非碎片（金币等）原样退
           洗练：星级材料**原样退**，不做任何折算
经验处理   两者相同：Σ(职业 job 从 1 级到当前等级-1 的 NeedEXP) → 经验珠
           经验珠换算对齐 global.Exp2ExpItems：面额从大到小贪心，余数丢弃
免费洗练   Forge.Free.Rate = 70 → 材料与经验都 ×70% 后向上取整
付费洗练   Forge.Charge 按伙伴**品质**匹配（Q7 → 元宝 ×2500），扣完退全额
```

配置来源（全部用 `config.xml`，节点名原服拼写就是 `partener`，不是 `partner`）：

```
/Config/partener/decompose/stage     quality=7 starlevel=5 rate=50 id=95
/Config/partener/forge/free          rate=70
/Config/partener/forge/charge        quality=2/3/4/6/7/8 → id=5 num=500..3000
/Config/partener/exp/range           94:1500 30:1万 31:5万 32:10万 33:50万 34:100万
```

这些字段在 `CFG_XMLConfig` 里**早就解析好了**（`Partener.decompose`、
`PartenerPayRecastingDic`、`PartenerEXPBeadDic`、`Partener.forgeRate`），
只是从没被业务代码用过。

### 60.3 实现要点

| 位置 | 改动 |
|---|---|
| `PartnerService.Compose` | 重复拥有先拦 → 碎片全量校验 → 全扣 → `AddPartner`；`AddPartner` 返回非 1 时**回滚碎片** |
| `PartnerService.Disassemble` | Quality/Starlevel 门槛 → **背包能装下全部待卸装备**才继续 → 聚合星级材料 → 碎片折算 → 加经验珠 → 发放 → `ResetPartner` |
| `PartnerService.Reforge` | 等级 >1 才可洗；免费走 70%，付费按品质扣道具 → 材料/经验原样（或 70%）退 → `ResetPartner` |
| `PartnerService.ResetPartner` | 清技能槽 → `Star=0 / Level=1` → 卸下全部装备回包 → `Skills.Clear()` 后重学 0 星技能 |
| `PartnerService.ExpToItems` | 经验 → 经验珠，**手写插入排序**（见 60.5 坑 2） |
| `GamePlayLocalHandlers` | 三个 `RegUnsupported` → `OnPartnerCompose` / `OnPartnerDisassemble` / `OnPartnerReforge` |

**背包容量前置校验**（`CanTakeOffAllEquips`）是本轮特意加的偏离：
原服是逐件 `changeEquip(2)`，背包满时后面的装备会留在空槽里。
重置后槽位已经没人，装备既不在背包也不在身上 —— 这是上一轮 58 节里
同类 P0（下阵不脱装备）的翻版，所以这里改成「先算件数、装不下就直接拒绝」。

### 60.5 两个 ILRuntime 真实坑（会写成 StackOverflow，极难定位）

**坑 1：热更代码里不能给 `List<T>.Sort` 传 lambda**

```csharp
ordered.Sort((a, b) => b.Value.CompareTo(a.Value));   // 💥
```

ILRuntime 会抛
`KeyNotFoundException: Cannot find Delegate Adapter for: PartnerService/<>c.<ExpToItems>b__20_0(...)`，

改成手写插入排序，零委托。

**坑 2：这个异常在测试里表现为「栈溢出」，完全误导**

第一次跑出来的是
`System.StackOverflowException at RuntimeStack.InitializeFrame`，

真实原因只是上面的委托适配器缺失 —— ILRuntime 在 `CLRMethod.Invoke` 里
处理异常时把栈耗尽了。

> 排查手段：`RunPartnerReset` 里加 `Log.Print("[pr] stepN")` 逐步打点 +
> 补 `catch (System.Exception e)`（原来只有 `try/finally`，异常冒到
> `TryRun` 的外层 catch，会新建一个空 `CaseResult`，**所有已通过断言全丢**，
> 这也是为什么第一次报告里只剩一条 FAIL）。

### 60.6 顺手修的一条脆弱断言（既有问题，与本轮功能无关）

## 61. 伙伴装备四段套装加成（2026-10-28）

补完 `Partner.refreshStats` 的最后一段：魂石自然加成 / 魂石大师 / 强化大师 / 升星大师。
至此伙伴属性与玩家属性走的是**同一套规则**。

### 61.1 四段判定规则

| 段 | 判定 | 配置来源 |
|---|---|---|
| 魂石自然加成 | 同一件装备的 **4 个魂石槽 NatureMark 全部相同** → 加 `EquipMaster(4000 + NatureMark)` | equipmaster.json Category=4（4001..4004） |
| 魂石大师 | 全身魂石 itemlevel 降序，按 `Diamond/master/stage` 的 num **从大到小**逐档：魂石数 ≥ num 且第 num 高的等级 ≥ 该档 Limit → 命中即 break | config.xml `Diamond/master/stage` + equipmaster Category=3 |
| 强化大师 | **全身最低强化等级**（空槽按 0）≥ Limit 的**最高一档** | equipmaster Category=1（Limit 5..50） |
| 升星大师 | **全身最低星级**（空槽按 0）≥ Limit 的**最高一档** | equipmaster Category=2（Limit 5..30） |

⚠️ **「全身最低」是原服语义，不是笔误**：原服遍历固定 `[MaxEquipSlot]Slot` 数组，
空槽的 `Enhance`/`Stars` 都是 0。所以少穿一件、或某一件没强化，强化大师就不生效。
本地原来只遍历「有装备的槽位」，必须改成遍历全部 13 个槽（0 号空置）才能对齐。

### 61.2 复用而非复制

`RoleStatService.AddGemstoneMaster`（魂石大师）本来就是玩家/伙伴通用的判定，
只是原来是 `private`。本轮放开成 `public`，伙伴侧直接调用 —— 避免同一套档位逻辑写两份、日后改一处漏一处。
`GemStoneNatureMasterBase = 4000` 同理改成 `public const`。

新增两个伙伴侧私有方法：

```
AddPartnerGemstones(values, equip, allGemLevels)   单件装备的魂石段 + 自然加成 + 收集 itemlevel
AddEquipMasterByLimit(values, category, achieved)  按 Category + Limit 取最高达标档
```

### 61.3 顺序调整（关键）

原实现把魂石段放在 `if (equip.Item == null) continue;` **之后**，
而原服是先处理 `equip.Gemstone` 再判 `equip.ItemId == 0`。已调整为：

```
魂石段（不依赖装备本体）→ if (Item == null) continue → 装备基础/强化/升星/极品属性
```

否则「槽位里有魂石但装备被摘掉」时魂石属性会凭空消失。

### 61.4 原服两处问题（本地按正确语义处理）

**① 自然加成写成了「取不到配置就跳过整个部位」**

```go
gemNatureCfg, ok := global.GetEquipMaster(...)
if ok != nil { continue }        // ← continue 掉的是整个部位的循环体，
                                 //   连后面的装备基础属性一起没了
```
本地只跳过自然加成本身。

**② 魂石生命百分比是 `setStats` 覆盖而非 `changeStats` 累加**

```go
par.stats.setStats(MAX_HEALTH, gemHealthAdd * HEALTH_PERCENTAGE / BaseRate)
```
等于把生命值**覆盖**成一个小数值。本地沿用玩家侧的写法（基于当前累计生命叠加）。
