# 单机化改造技术评估

> 时间：2026-10-24
> 目标：把 client 改造成**可正常运行的纯单机游戏**（TapTap 小游戏为终态）
> 本期边界：
> - ✅ 删除真多人内容（公会 / 聊天 / PVP / GVG / 世界 Boss / 排行榜 / 观战）
> - ✅ 机器人保留（回合制对手要用）
> - ✅ 充值项目**先保留不动**，后面接广告时再调
> - ✅ 服务端逻辑 → 客户端本地逻辑
> - ✅ 存档：本地 or 云端（先本地，接口预留）

---

## 0. 结论

**这件事的技术难点非常集中：不是「改 128 个界面」，而是「把 7,000–8,000 行战斗与成长核心从 Go 搬到 C#」。**

好消息有两条：
1. **协议层可以做到零改动** —— 只要本地实现吐出的 protobuf 字节和真服务端一致，`ProtoC` 的 105 个下行处理和 128 个 UI **一行都不用改**。
2. 单人核心占七成，改造成本集中在战斗，其余（背包/任务/活动/商店）是数据搬运，难度低。

真正要警惕的一条：
> 🔴 **7,000 行战斗逻辑放进 ILRuntime 热更层跑，WebGL 上会崩性能。** 这块必须并进 AOT 编译。（详见第 5 节）

---

## 1. 现状：逻辑分布

### 1.1 战斗全在服务端

| 能力 | 位置 | 客户端有没有 |
|---|---|---|
| 扣血 / 死亡 | `map_object.go:459 changeHp()` | ❌ 只播动画 |
| Buff / DOT | `map_object.go:543 processBuff()` | ❌ |
| 属性计算 | `map_object.go:940 refreshStats()` | ❌ |
| 攻击判定 / 射程 | `map_object.go:200 CanAttack()` / `inAttackRange()` | ❌ |
| 技能释放 | `player.go:3846 attack()` | ❌ |
| 怪物 AI | `monster_mgr.go:1094 processAI()`（含游荡/索敌/寻路/攻击） | ❌ |
| 伙伴 AI | `partner.go:1047 attack()` | ❌ |
| 掉落 | `monster_mgr.go:290 drop()` | ❌ |
| 游戏循环 | `timer.go:122 TimerForSecond()` + `desk` tick | ❌ |

客户端 `Role.SetAttack()`（`Role.cs:628`）只做两件事：**播动作、播特效**。所有数值都等服务端下发。

⇒ **单机化的本质 = 把这套战斗系统重建到客户端。**

### 1.2 必须移植的模块（量化）

| 模块 | 行数 | 内容 | 难度 |
|---|---|---|---|
| `map_object.go` | 1,710 | 战斗对象基类：属性/Buff/扣血/攻击判定/射程 | 🔴 高 |
| `partner.go` | 1,487 | 伙伴属性 + AI | 🟡 中 |
| `monster_mgr.go` | 1,231 | 怪物 AI（游荡/索敌/**A\* 寻路**/攻击/掉落） | 🔴 高 |
| `player.go` 战斗与成长部分 | ~2,000（估） | 玩家攻击、升级、属性刷新 | 🟡 中 |
| `skillmgr.go` | 484 | 技能效果与冷却 | 🟡 中 |
| `logic_mow.go` | 325 | 挂机刷怪 | 🟢 低 |
| `timer.go` | 125 | 定时重置（每日/零点） | 🟢 低 |
| **战斗小计** | **≈ 7,400** | | |
| 数据管理（背包/任务/活动/商店/邮件） | ≈ 8,000 | 相对简单，纯 CRUD + 配置查表 | 🟢 低 |
| 多人部分（**删除，不移植**） | ≈ 4,500 | 公会/聊天/PVP/世界Boss | — |

### 1.3 一个容易漏的点

`monster_mgr.go:868 moveTo()` 用的是 **`astar.APoint`** —— 服务端依赖 Go 的 A* 寻路库。

客户端要么移植这个寻路，要么换成 Unity 的寻路方案。**但两边寻路结果不一致会导致怪物走位差异**，进而影响命中判定。建议直接移植同一套 A*，保证行为一致。

## 2. 目标架构

```
  UILogin / UIHall / UIGameDungeons …（128 个界面）   ← 不改
                    ↓
  ProtoC（105 个下行处理）                            ← 不改
                    ↓
  TcpC / HttpC（137 条路由 + 40 个接口）              ← 只换下层实现
                    ↓
  ┌─────────────────────────────────────────┐
  │  新增：LocalServer（协议应答层）          │
  │    · 输入：与真服务端完全一致的 protobuf  │
  │    · 输出：与真服务端完全一致的 protobuf  │
  └─────────────────────────────────────────┘
                    ↓
  ┌─────────────────────────────────────────┐
  │  新增：GameCore（从 Go 移植）             │
  │    · 战斗核心（map_object/monster/partner/skill）
  │    · 数据管理（背包/任务/活动/商店）
  │    · 游戏循环（tick 驱动 AI / Buff / 冷却）
  └─────────────────────────────────────────┘
                    ↓
  ┌─────────────────────────────────────────┐
  │  新增：SaveProvider（存档抽象）           │
  │    · LocalFileProvider（先做）            │
  │    · CloudProvider（预留，后接）          │
  └─────────────────────────────────────────┘
```

### 2.1 唯一的关键设计原则

> **LocalServer 必须吐出一模一样的 protobuf 字节。**

只要守住这条：
- 105 个下行处理不用改
- 128 个界面不用改
- 将来想换回真服务端，改一行开关就行

**这是整个改造的护城河，破坏它就等于重建客户端。**

## 3. 分阶段计划

每一阶段结束都能真实运行、真实验收，不憋大招。

### 阶段 1 · 协议层接管（非战斗）— 主线第一步

| 项 | 内容 |
|---|---|
| 做 | `LocalServer` 框架 + 非战斗协议本地化：登录、角色、背包、任务、邮件、商店、活动、签到 |
| 不做 | 战斗仍连本地 Go 服 |
| 验收 | 断掉 Go 服也能登录进主城，背包/任务/签到/商店全部可点可操作 |
| 价值 | 验证「协议零改动」这个架构假设；打通存档链路 |

### 阶段 2 · 战斗核心移植

| 项 | 内容 |
|---|---|
| 做 | `map_object` → `monster` → `partner` → `skill`，按依赖顺序；游戏循环 tick；A* 寻路对齐 |
| 验收 | 进副本能打怪、怪物会追人、掉血数值和现在一致、能结算 |
| 风险 | 本阶段是全部工作量的大头 |

### 阶段 3 · 全量本地化 + 删多人

| 项 | 内容 |
|---|---|
| 做 | 剩余协议全切本地；删公会（12 UI + 17 协议 + `guild_manager.go`）、聊天、PVP/GVG、世界 Boss、排行榜、观战、选服/手机登录/实名 |
| 保留 | **机器人系统**（`robotmgr.go`，回合制对手用） |
| 验收 | 完全断网可玩全流程；点不到任何多人入口 |

### 阶段 4 · 存档

| 项 | 内容 |
|---|---|
| 做 | 本地存档（`Application.persistentDataPath`）+ 自动保存 + 版本迁移 |
| 预留 | `SaveProvider` 抽象成接口，云端实现留空 |
| 验收 | 退出重进数据不丢 |

### 阶段 5 · 广告化（本期不做）

付费点换广告引擎 + 文案清洗，按 `单机化功能模块梳理.md` 第 10 章执行。

## 4. 存档方案

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **本地文件**（JSON/二进制 → `persistentDataPath`） | 零成本、离线可用 | 清缓存即丢档、换机丢档 | ✅ **先做** |
| 云端（自建 or 平台能力） | 换机不丢 | 要后端、要联网 | 🟡 接口预留，后接 |

**实施要求**：业务侧只认 `ISaveProvider`，不直接写文件。这样以后上云只加一个实现类。

存档内容 = 服务端 DB 里那些表（玩家 / 背包 / 任务 / 伙伴 / 宠物 / 活动进度），字段结构直接照搬服务端 model，避免二次设计。

---

## 5. 🔴 必须提前决定的技术问题：战斗逻辑放哪

这是本方案唯一的架构级风险。

| 放法 | 后果 |
|---|---|
| 放进 `HotUpdateScripts`（ILRuntime 解释执行） | 7,000 行战斗逻辑 + 每帧 tick，**WebGL 上必然卡**（ILRuntime 无 JIT，且官方说 WebGL 只有 Native 1/3 性能，两者叠加） |
| **并进 AOT**（`Assets/Scripts/` 编译进 Assembly-CSharp） | 性能原生；但**改代码必须重编 Unity**，失去热更便利 |

**我的建议：战斗核心（GameCore）走 AOT，UI/业务层留在热更层。**

理由：
1. 单机化之后**热更的价值本来就大幅下降**（没有线上要热修的东西）
2. 战斗是每帧跑的逻辑，性能敏感度最高
3. UI 层 128 个界面留在热更层，改文案/调布局仍然方便

> 这条如果现在不定，阶段 2 写到一半再改架构会推翻重来。

## 6. 其余风险清单

| # | 风险 | 等级 | 对策 |
|---|---|---|---|
| 1 | **数值一致性**：C# 移植与 Go 有偏差，玩家能明显感觉伤害不对 | 🔴 高 | 每个模块移植后用同一份输入对拍（Go 侧跑一遍、C# 侧跑一遍，比对输出） |
| 2 | **A\* 寻路行为差异** | 🔴 高 | 移植同一套 A*，不要换 Unity 原生寻路 |
| 3 | **时序差异**：服务端固定 tick，客户端帧率波动 | 🟡 中 | 客户端用固定步长累加器（fixed timestep accumulator）模拟服务端 tick |
| 4 | 协议字节不一致导致 UI 静默失败 | 🟡 中 | 阶段 1 就建立「同一请求 → 比对 Go/C# 响应字节」的自动化对拍 |
| 5 | 删多人时误伤回合制框架（desk/room/match） | 🟡 中 | 批次顺序：先删公会（独立文件），最后动框架 |
| 6 | 存档格式后期要改，老档失效 | 🟢 低 | 存档带 `version` 字段 + 迁移函数 |

## 7. 现在就可以定的三件事

| # | 决策 | 影响 |
|---|---|---|
| 1 | **战斗核心走 AOT 还是热更** | 决定阶段 2 的代码放哪，晚定会返工 |
| 2 | **存档先本地还是直接上云** | 建议先本地 + 接口预留，不要一上来做后端 |
| 3 | **移植顺序：先数据后战斗，还是先战斗后数据** | 建议**先数据**（阶段 1），因为能最快验证"协议零改动"这个假设 |

## 8. 一句话总结

**改 128 个界面是假象，真正要做的是把 7,400 行战斗逻辑从 Go 搬到 C#，并保证它跑在 AOT 上不掉帧。协议层只要守住「字节一致」，UI 就一行都不用动 —— 这是能省下几个月的关键。**
