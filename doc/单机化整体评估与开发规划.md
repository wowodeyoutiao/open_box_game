# 单机化整体评估与开发规划

> 评估对象：`game_machao` 当前 Unity 客户端、本地 C# 模拟服务与 Go 原服务端  
> 评估依据：当前源码、Prefab/配置及现有文档  
> 本文定位：当前阶段的架构结论、问题清单和开发基线。旧文档与本文冲突时，以当前源码和本文为准。

---

## 1. 结论先行

### 1.1 架构方向是对的，但当前只是“可进大厅的早期骨架”

继续采用“保留客户端协议和 UI，在发送层切换到本地 Service”的方向是合理的。它能复用 `TcpC`、`HttpC`、`ProtoC`、Manager 和大量 UI，避免把整个项目重写成另一套客户端。

但不能把当前状态称为“完整单机游戏”，原因有六个：

1. **TCP 未实现协议会被吞掉且无响应**，调用方可能一直等待。
2. **HTTP 未命中本地路由后仍会访问真实网络**，发布版尚不能保证离线。
3. **多个动作协议只返回 `Code = 0`**，界面显示成功，权威数据却没有变化。
4. **存档实现仍为空**，重启不能保存真实进度。
5. **战斗服务为空，大厅挂机只是 UI 驱动的表现循环**，没有完整命中、伤害、怪物攻击、死亡和奖励闭环。
6. **角色属性仍有硬编码，建角、背包、装备、技能和伙伴数据没有统一初始化规则。**

因此，当前最合理的定位是：**协议适配层已验证可行，接下来应集中建设本地领域规则、存档和核心玩法闭环，而不是继续增加空响应。**

### 1.2 不建议把 Go 服务端进程、MySQL、Redis 一起塞进客户端

应迁移的是：

- 个人角色进度；
- 装备、背包、技能、伙伴、宠物等领域数据；
- 属性、伤害、掉落、任务、挂机等确定性规则；
- 必要的配置和随机规则；
- 原协议对应的响应与推送语义。

不应迁移的是：

- Nano 网络服务、HTTP 服务、Session 和网关；
- MySQL、Redis、EventBus、全服定时器等运行基础设施；
- 后台管理、GM、支付回调、真实账号体系；
- 公会、聊天、真人 PVP、GVG、世界 Boss 等多人规则。

旧文档提出过 Go-WASM 路线，但当前项目已经实际走上纯 C# `LocalServer + Service` 路线。除非目标平台性能或移植成本出现新的阻断证据，否则不建议现在反复更换技术路线。

### 1.3 后续开发的核心不是“补协议数量”，而是“完成领域闭环”

一个功能只有同时满足以下条件，才能标记为完成：

```text
请求校验通过
→ 修改 LocalData 中的权威数据
→ 必要的属性/任务/冷却联动完成
→ 存档可保存
→ 响应与推送同步到 ProtoC / Manager
→ UI 显示与数据一致
→ 重进游戏后结果仍正确
```

`Code = 0`、界面能打开、数组不为空，只能说明“兼容桩存在”，不能说明玩法完成。

## 2. 当前架构评估

### 2.1 当前真实数据流

当前本地模式并不是严格的“protobuf 字节进、字节出”，而是：

```text
UI
→ TcpC / HttpC
→ TCPClientMgr.SendMessage / HttpRequestHelper
→ LocalServer / LocalHttpRouter
→ PlayerService / ItemService 等
→ 直接构造响应对象
→ JEvent.defaultEvent.Post(response)
→ ProtoC 已有处理方法
→ RoleM / BagM 等客户端镜像
→ UI
```

直接投递响应对象有现实价值：它规避了 ILRuntime、LitJson、protobuf-net 反序列化时空集合变成 `null` 等兼容问题，可以保留。

但需要修正文档和测试策略：

- 不再宣称当前已经做到字节级协议完全一致；
- 把兼容性保证落实到“响应对象字段、集合、推送顺序和 Manager 结果一致”；
- 对关键玩法建立原服与本地实现的领域级对拍，而不是只验证能否收包。

### 2.2 应保留的分层

| 层 | 当前/建议组件 | 正确职责 | 不应承担的职责 |
|---|---|---|---|
| Adapter | `LocalServer`、`LocalHttpRouter` | 命令/URL 路由、参数适配、异常转响应 | 属性计算、发奖、背包修改 |
| Domain Service | `PlayerService`、`ItemService`、`BattleService` 等 | 校验、规则计算、状态变更、构造结果 | 直接操作 UI、依赖网络 Session |
| 权威数据 | `LocalData`、`LocalRole` 及后续领域数据 | 保存唯一真实进度 | 当作客户端临时显示缓存 |
| 存档 | `ISaveProvider` | 加载、保存、版本迁移、备份恢复 | 保存 RoleM/BagM 等派生镜像 |
| 推送 | `LocalPusher` 或后续领域事件调度 | 把已发生的数据变化同步给客户端 | 自己决定奖励、伤害等业务结果 |
| 配置 | 现有客户端 JSON/XML，按需补服务端独有表 | 提供只读规则参数 | 在 Service 中重复硬编码同一数值 |
| 客户端镜像 | `RoleM`、`BagM`、`PartnerM` 等 | 接收推送、供 UI 读取 | 反向覆盖权威进度 |

Service 之间允许单向依赖，例如 `BattleService` 可以读取角色、装备和伙伴服务；禁止形成循环依赖。

### 2.3 必须优先修正的架构缺口

#### A. 严格离线模式

建议明确区分两种模式：

- **单机发布模式**：所有保留功能的 TCP/HTTP 请求必须本地处理；未命中路由直接报清晰错误，禁止回退真实网络。
- **联机对照模式**：仅开发环境显式开启，用于抓包、对拍和排查，不得被单机发布配置继承。

验收方式不是只看 `LocalServer.Enabled = true`，而是断网冷启动后完整走完主流程，并确认没有真实网络回退日志。

#### B. 未实现协议不能无声等待

当前 `LocalServer.TryHandle()` 对未注册命令仍返回 `true`，但 `response == null`。这代表“已接管”，却不给调用方任何终态。

需要建立协议台账，并为每条入口协议标记：

- 已实现；
- 明确禁用，入口同步隐藏；
- 兼容空响应，仅限纯查询且不会影响进度；
- 待实现，返回可识别的失败结果并记录；
- 不允许再出现“动作成功但无状态变化”。

异常处理也不能只记日志后返回空响应，否则结果与未实现协议相同。

#### C. 清理假成功

`GamePlayLocalHandlers` 当前对下列动作统一返回成功：

- 角色升级；
- 宝箱设置、升级、快速升级；
- 伙伴上阵、合成、分解、重铸、替换、休息、升星；
- 宠物升级；
- 一键装备；
- 战斗奖励。

这些协议应从通用成功桩中逐步移除，迁移到对应 Service。未迁移前应在功能台账中标为“假成功”，不能计入完成度。

#### D. 权威数据不能无限堆进一个类

原服务端 `User` 覆盖背包、技能、装备、任务、Buff、爬塔、命格等大量字段；当前 `LocalRole` 只覆盖很小一部分。后续可以按领域拆成角色、背包、装备、技能、任务、挂机等数据组件，由一个角色存档聚合，而不是持续把所有字段塞入同一个类。

当前 `LocalRole.Clone()` 没有复制 `BagData`、`Partners`、`Equips`。在存档、导入导出或角色复制复用它之前必须修正，并明确深拷贝规则，避免数据丢失或多个角色共享可变对象。

## 3. 挂机界面四个问题的根因分级

这四个现象不是同一个 Bug，也不能靠一个“战斗开关”一起解决。

| 问题 | 已由代码确认 | 高概率原因/待实机确认 | 正确处理方向 |
|---|---|---|---|
| 怪物朝右不朝左 | 生成代码已经设置负 X 缩放；Prefab 自身没有额外负缩放 | Spine 原画默认朝向、`SkeletonGraphic.initialFlipX`、父级缩放、对象池复用状态需要联合检查 | 统一封装朝向控制，以“面向玩家”为准，不在多个位置重复翻转 |
| 怪物没有攻击动作 | 怪物加载后只设父节点、位置、缩放；`OnSetAnim()` 没控制 `MonsterObj`；Prefab 默认循环 `stand` | 资源字符串中可见 `attackH`，但需在 Unity/Spine 中确认准确动画名和事件帧 | 建立怪物 idle/attack/hurt/dead 表现状态机，由战斗事件驱动 |
| 玩家攻击没特效 | 特效在怪物异步加载完成前就可能调用；当前一次遇怪只调用一次，并非每次命中触发 | 替代特效的 UI 渲染层级、粒子播放、对象池重播、原始缩放被覆盖仍需实机检查 | 特效绑定实际目标与攻击命中事件；处理异步生命周期、Sorting 和池化重播 |
| 玩家身上看不到装备 | 原服创角装备主要通过邮件赠送；当前默认角色直接穿 4 件、背包放 2 件，但新建角色没有执行这套初始化 | UI 装备槽与人物外观是两条链路；当前主角模型只按职业/性别选择 | 统一新角色初始化；另行决定是否需要纸娃娃/武器外观，不能把装备数据存在等同于模型会变化 |

### 3.1 怪物朝向

`UIHall` 已存在类似以下逻辑：

```csharp
bool flipX = true;
go.transform.localScale = new Vector3(-scal, scal, 1f);
```

所以问题不是“漏写负缩放”。继续盲目再乘一次 `-1`，很可能只在某种资源或某次池化后碰巧正确。

最小排查顺序：

1. 确认该怪物 Spine 原画默认朝左还是朝右；
2. 运行时检查根节点、父节点和 Skeleton 的实际缩放/翻转状态；
3. 检查对象池取出时是否恢复了旧状态；
4. 只保留一个朝向入口，首次生成和重复遇怪都调用同一方法。

验收：不同怪物、首次生成、对象池复用、切换角色再进大厅后，怪物始终面向玩家。

### 3.2 怪物攻击动作

`moester.prefab` 默认动画是 `stand`，代码又没有显式播放怪物攻击动画，因此“一直站立”是符合当前代码的结果。

可以分两步处理：

- **表现修复**：先验证并播放正确攻击动画，攻击结束后回 `stand`，死亡时播放 `dead`；
- **玩法闭环**：后续由本地战斗状态机决定何时攻击、何时命中、何时死亡，UI 只消费事件，不再自行决定战斗结果。

不要仅把怪物攻击动画和玩家动画同时循环播放，就宣称战斗完成。

### 3.3 玩家攻击特效

当前至少存在一个确定的时序问题：怪物通过 `GameHelper.SetAsyncObj()` 异步创建，而攻击特效可能在 `MonsterObj` 尚未 ready 时触发，只能回退到主角附近或找不到目标。

建议攻击表现链路统一为：

```text
本地攻击事件
→ 确认施法者和目标仍然存在
→ 播放攻击动画
→ 到命中帧/命中事件
→ 在目标挂点生成特效
→ 处理伤害飘字和受击
→ 特效播放完成后归还对象池
```

对象池取出后需要明确 `Clear/Stop/Play` 和激活状态；UI 粒子还要验证 Canvas、Camera、Sorting 与遮罩。特效 Prefab 根节点原始缩放为 `(150,150,150)`，当前代码覆盖为 `Vector3.one`，也应纳入可见性检查，不能只凭“资源已替换”判断完成。

验收：第一轮遇怪、后续每轮、目标死亡/切换、连续多次攻击时，特效都在正确目标位置出现且只出现一次。

### 3.4 初始装备与人物外观

原服 `login.go` 在创角后调用 `CreateRoleSendProps()`，创建“登录送装备”系统邮件；这说明原项目的设计主要是**创角后从邮件领取装备**，不是出生就全部穿在身上。

当前本地却有两套不一致的规则：

- `LocalData.Reset()`：直接穿戴 101～104，背包放 105～106；
- `PlayerService.BuildCreateCharResponse()`：只创建基础角色，没有初始化背包、装备、技能、伙伴和邮件。

建议单机版采用更清晰的规则：**所有新角色统一初始化新手装备并直接穿戴，少量练习装备放背包；不再同时发一份可重复领取的同内容邮件。** 如果产品更希望保留邮件教学，也可以恢复邮件方案，但只能选一种权威来源，并保证领取幂等。

同时必须区分：

- **装备数据可见**：装备栏、背包和属性是否正确；
- **装备外观可见**：人物模型是否根据武器/装备变化。

当前 `SetRoleSpine()` 只按职业和性别选择固定模型，因此即使装备数据正确，人物身体也不会自动变成纸娃娃外观。若只需要装备栏和属性反馈，无需扩建纸娃娃；若要求武器或时装体现在人物身上，应单独立项。

## 4. 服务端迁移范围与模块矩阵

### 4.1 迁移原则

1. **按个人领域迁移，不按 Go 文件逐行翻译。** `player.go` 同时含大量个人、多人和平台逻辑。
2. **原服不是完整标准答案。** 原服自身存在签到发奖、VIP、批量开箱校验、广告和充值等 TODO。
3. **先核心闭环，后外围数量。** 不要先迁公会或所有活动，再发现没有存档和战斗。
4. **复用协议语义，不复制服务端基础设施。**
5. **每个模块同时交付数据、规则、推送、存档和测试。**

### 4.2 保留并本地化的个人系统

| 模块 | 原服参考 | 当前本地状态 | 迁移内容 | 优先级 |
|---|---|---|---|---|
| 本地启动与角色 | `web/api/login.go`、玩家基础数据 | 登录/建角/选角可走通，初始化不统一 | 本地档案、创角、选角、删角、统一新手初始化 | P0 |
| 存档 | MySQL/Redis 中的个人数据语义 | Provider 全为空 | 版本化存档、加载、保存、备份、迁移、WebGL 持久化验证 | P0 |
| 背包与道具 | `player.go` 背包/道具相关方法、Item 配置 | 简单读取，规则不全 | 容量、堆叠、唯一 UID、使用、出售、合成、分解、满包处理 | P0 核心，完整 P1 |
| 装备 | 装备穿脱、强化、升星等 | 基础穿脱，缺完整校验与重算 | 部位/职业/等级校验、一键穿戴、强化、升星、属性联动 | P0 基础，进阶 P1 |
| 角色属性与成长 | Role 配置、Global 公式 | 攻/防/战力等硬编码 | 基础属性、等级经验、装备/技能/伙伴加成、战力公式 | P0 |
| 大厅挂机 | `player.go` 在线挂机、`logic_mow.go` | UI 每 6 秒自驱遇怪 | 活力时间、遇怪节奏、奖励、背包检查、满包转系统信、离线收益 | P0 |
| 宝箱 | `player.go`、TreasureBox/OpenBox 配置 | 多个升级动作是假成功 | 开箱、队列/冷却、升级、加速、批量校验、掉落 | P1，挂机依赖部分提前 |
| PVE 实时战斗 | `map_object.go`、`monster_mgr.go`、`skillmgr.go`、`timer.go` | `BattleService` 空 | 固定 tick、属性、技能、命中、伤害、AI、寻路、死亡、结算 | P0 最小闭环，完整 P1 |
| 副本与关卡 | `battle` 配置、副本入口与结算 | 列表为空 | 解锁、进入、消耗、胜利/失败、奖励、扫荡、章节进度 | P0 首个副本，扩展 P1 |
| 任务 | `task_mgr.go` | 空 | 任务状态、事件计数、领奖、章节/日常任务 | P1；战斗事件接口 P0 预留 |
| 技能 | `skillmgr.go`、Skill 配置 | 登录槽位为空 | 解锁、升级、装备槽、冷却、战斗释放 | 基础随 P0 战斗，养成 P1 |
| 伙伴 | `partner.go`、Partner 配置 | 空槽，多数动作假成功 | 获取、上阵、属性、AI、升级、升星、合成、分解 | 基础战斗单元 P1 |
| 宠物 | 宠物记录与配置 | 宠物升级为假成功 | 获取、展示、升级、奖励和属性联动 | P1/P2 |
| 圣物/命格/Buff | 对应个人字段和配置 | 未形成完整数据 | 解锁、加成、持续时间和战斗效果 | P1/P2 |
| 邮件 | `web/api/mail.go` | 本地空列表 | 改为系统信；奖励附件、领取幂等、满包补发 | P1；挂机满包需要的基础能力提前 |
| 签到与单人活动 | `web/api/sign.go`、Activity 配置 | 多数返回空集合 | 本地日期、签到发奖、单人任务活动、奖励领取 | P2 |
| 商店 | `web/api/store.go`、Store 配置 | 空列表 | 游戏币商店、刷新、购买校验；不接真实支付 | P2 |
| 回合制 AI 玩法 | desk/room/match/robot | 未迁移 | 仅复用本地对局和机器人所需部分，去真人匹配/排行 | P2 |

### 4.3 原服 TODO 的分类处置

| 原服待实现项 | 单机处置 |
|---|---|
| 签到奖励未发放 | 若保留签到，必须补真实规则，不能照抄空实现 |
| VIP TODO | 重新定义无付费成长/广告权益，不迁原充值语义 |
| 批量开箱数量校验缺失 | 宝箱实现时补校验和原子扣除 |
| 广告直接通过、充值 TODO | 视为未设计；先在无广告环境下提供可测试接口，再接平台能力 |
| 订单发奖和支付状态 | 不迁移，真实支付链路删除 |
| 好友邮件校验 | 随社交邮件删除 |
| 机器人榜单按战区存储 | 单机排行删除；本地 AI 对手不需要该逻辑 |
| MySQL 同步 Redis、SQL 安全等 | 属于原基础设施，不迁移 |

### 4.4 删除、禁用或重写的系统

| 类型 | 内容 | 工程处置 |
|---|---|---|
| 多人社交 | 公会、聊天、好友社交邮件 | 隐藏入口 → 移除路由 → 清理 UI/引用 |
| 真人竞争 | 真人 PVP、GVG、观战、实时匹配 | 不迁移；保留回合制所需框架 |
| 全服共享 | 世界 Boss、全服伤害和跨服排行 | 删除或另做完全独立的单人玩法，不能假装原逻辑可直接本地化 |
| 平台联网 | 选服、手机登录、真实账号、实名自建流程 | 改成本地档案和平台必要能力 |
| 真实付费 | 支付绑定、订单、支付回调、充值发奖 | 不迁移并清除入口；奖励系统改为游戏内或广告触发 |
| 后台与运维 | GM、后台 API、Redis/MySQL/Nano 初始化 | 保留在原服作对照工具，不进入单机包 |

注意：`desk/room/match` 不能按目录全部删除，因为回合制玩法可能复用其中部分框架。删减应按调用链和规则边界进行。

### 4.5 配置迁移

现有审计表明，大部分客户端 JSON/XML 与服务端 XLSX 是同源导出，不需要重新建设一套配置系统。

按需补充：

- `ItemGroup`：掉落结算需要时优先补；
- `Robot`：做回合制本地 AI 时补；
- `LevelGift`：保留对应活动时补；
- `RandomCreat`：确认实际用途后再决定；
- 公会等已删除配置不补。

## 5. 推荐开发顺序

### 阶段 0：建立可信基线

**内容**

1. 增加严格离线模式，禁止发布版 HTTP 真网回退；
2. 建立 TCP/HTTP 功能台账，标出未实现、空查询、假成功和删除项；
3. 未实现/异常请求必须有明确失败终态，不能无声等待；
4. 固化关键原服请求、响应和领域结果作为对拍样本；
5. 更新过时文档，停止把“进大厅”写成“战斗和玩法已完成”。

**验收**

- 断网冷启动可进入当前已支持的大厅流程；
- 网络日志中没有非预期真实服务器访问；
- 所有已开放按钮都有明确结果，没有永久等待；
- 可以一键列出当前缺失协议和假成功协议。

### 阶段 1：完成一个新角色垂直切片，并修复大厅表现

**内容**

1. 用统一初始化入口覆盖默认角色、新建角色和存档迁移后的新角色；
2. 明确新手装备方案，保证 UID 唯一、穿戴与背包不重复、领取幂等；
3. 修复怪物朝向、怪物攻击和玩家命中特效；
4. 将 `UIHall` 中的遇怪/攻击表现整理成独立状态机，避免继续堆 UI 定时器；
5. 明确“装备数据”和“人物外观”各自验收范围。

**验收**

- 任一建角路径进入游戏，装备栏、背包和角色属性一致；
- 重登不会重复发放新手装备；
- 首次和后续遇怪均有正确朝向、双方攻击动作和命中特效；
- 退出重进大厅后状态可重置，无残留怪物或特效。

### 阶段 2：存档、真实背包装备与属性

存档不应再等所有玩法完成后才开始，否则大量临时数据结构会反复返工。应先交付可扩展的存档 V1，再随模块增加版本迁移。

**内容**

1. 实现 `ISaveProvider`，保存角色列表、当前角色和已完成的领域数据；
2. 增加存档版本、损坏恢复、备份和迁移机制；
3. 修复 `Clone()` 等深拷贝风险；
4. 完成背包容量、物品 UID、装备校验和穿脱；
5. 用配置替换硬编码属性，建立统一属性重算入口；
6. 让响应、推送和存档在同一领域操作后保持一致。

**验收**

- 穿戴/卸下装备后，属性与战力立即正确变化；
- 强退并重启后，角色、货币、背包、装备和关卡进度不丢失；
- 旧版本存档可迁移，损坏存档不会导致无法启动；
- 多角色数据不串档、不共享可变背包对象；
- 目标 WebGL 平台单独验证持久化，不以 Editor 测试代替。

### 阶段 3：把大厅挂机从动画升级为收益闭环

**内容**

1. 本地调度器驱动在线/离线挂机，而不是 `UIHall` 自行决定奖励；
2. 实现活力时间、遇怪间隔、随机奖励和离线时长上限；
3. 背包满时按规则转系统信或停止对应奖励；
4. 奖励操作幂等，防止重复点击、重登或恢复存档重复领取；
5. 表现层消费遇怪、攻击、死亡、掉落事件。

**验收**

- 相同随机种子和相同输入可复现收益；
- 在线、离线、背包满、跨天等边界结果正确；
- UI 动画和实际奖励一致，不因动画未播完而丢奖或重复发奖；
- 重启后挂机时间和未领取奖励可恢复。

### 阶段 4：PVE 最小战斗闭环，再扩完整战斗

**最小闭环优先内容**

1. 固定 tick 和随机种子；
2. 玩家/怪物战斗单元、生命、攻击、技能、命中与死亡；
3. 一个怪物 AI：待机、索敌、追击、攻击、死亡；
4. 一个副本：进入、消耗、胜利/失败、奖励、退出；
5. 战斗表现事件驱动动画、特效、飘字和结算 UI；
6. 记录关键输入与结果，和原服做领域对拍。

**后续扩展**

- A* 寻路与更完整 AI；
- 多技能、Buff、伙伴协战；
- 爬塔、圣物挑战、扫荡和章节奖励；
- 根据 WebGL 实测决定战斗继续放热更层还是迁往 AOT。

**验收**

- 伤害、冷却、死亡和结算不依赖动画时长或帧率；
- 同一种子和输入得到一致结果；
- 胜利只发一次奖励，失败不错误发奖；
- 低帧率、切后台和重复进入副本不会破坏状态；
- WebGL 实机性能达标后再决定代码归属，不提前做绝对判断。

### 阶段 5：扩展养成与任务

按依赖顺序推进：

1. 技能解锁/升级/槽位；
2. 任务事件与领奖；
3. 宝箱完整规则；
4. 伙伴基础获取、上阵和 AI，再扩展升星/合成/分解；
5. 宠物、装备强化/升星、圣物/命格；
6. 每接一个模块，就从假成功表和协议台账中核销对应项。

### 阶段 6：单人外围、删减与平台化

1. 系统邮件、签到、单人活动、游戏币商店；
2. 回合制 AI 玩法，按需复用 desk/room/robot；
3. 删除多人、社交、真实支付和选服等入口及路由；
4. 广告能力先完成独立样板，再接体力、复活、双倍、加速等具体点位；
5. 做 WebGL 包体、内存、帧率、持久化和长时间挂机测试；
6. 清理旧服务端依赖和无效配置，但保留原服作为开发期对照环境。

## 7. 测试与完成度管理

### 7.1 建立唯一的协议/功能台账

建议每条记录至少包含：

```text
协议或 URL
| 对应 UI/入口
| 保留/删除
| 当前 Handler
| 空桩/假成功/真实规则
| 权威数据字段
| 响应与推送
| 是否存档
| 测试状态
```

`MissingCmds` 可作为运行时辅助，但不能替代这份台账。

### 7.2 完成度定义

| 标记 | 含义 |
|---|---|
| 未接 | 没有本地路由或 UI 尚未接 |
| 兼容桩 | 仅避免崩溃，返回空集合或默认信息 |
| 假成功 | 返回成功但不修改权威数据，必须清零替换 |
| 规则完成 | 校验、数据变化、响应/推送和异常路径完成 |
| 可存档 | 重启后状态保持一致，含版本迁移 |
| 可交付 | 表现、边界测试、目标平台验证均通过 |

### 7.3 必做测试类型

- **领域单元测试**：属性、背包、装备、掉落、任务、奖励幂等；
- **协议响应测试**：必要字段、空集合、`RequestCmdId`、推送顺序；
- **原服对拍**：同配置、同输入、同随机种子比较关键结果；
- **存档回归**：新档、旧档、损坏档、多角色、强退恢复；
- **表现测试**：首次异步加载、对象池复用、切场景、目标中途死亡；
- **目标平台测试**：WebGL 的持久化、内存、帧率和后台恢复。

## 8. 主要风险与控制措施

| 风险 | 后果 | 控制措施 |
|---|---|---|
| 继续用空成功补界面 | 表面完成度高，实际大量返工 | 动作协议禁止通用 `Code=0` 作为完成方案 |
| 所有逻辑继续堆入 `UIHall` | UI、战斗、奖励互相耦合 | UI 只消费事件，规则进入 Service |
| 存档做过晚 | 数据结构调整导致重复迁移和丢档 | 阶段 2 先落地可扩展 V1 |
| 新旧角色初始化不一致 | 装备、技能和存档表现随入口变化 | 统一初始化用例，所有入口复用 |
| 原服自身有 TODO | 迁移后仍缺规则 | 将原服分“可对照规则”和“需重新设计”两类 |
| 盲目翻译整个 Go 工程 | 带入多人、支付和基础设施 | 按个人领域和调用链迁移 |
| 过早决定战斗必须 AOT | 增加热更与调试成本 | 先保持边界，WebGL 实测后决策 |
| 仅 Editor 验证 | 发布后才暴露持久化/性能问题 | 每个核心阶段都安排 WebGL 验证 |
| 旧文档状态冲突 | 排期和验收基于错误事实 | 源码为事实源，本文作当前计划基线 |

## 9. 最终建议

当前不需要推翻重来，也不需要把 Go 服务端完整搬进 Unity。最划算的路线是：

> **保留本地协议适配方向，停止扩张空实现；先修数据初始化、离线和存档基础，再完成真实挂机收益与 PVE 战斗闭环，最后扩养成、活动和广告。**

最近的实际开发顺序建议收敛为：

1. 严格离线、异常终态、协议/假成功台账；
2. 配置加载后真正启动本地装配，并实现存档 V1；
3. 统一新角色初始化和三职业新手装备；
4. 修复大厅朝向、怪物攻击和命中特效（作为可并行的最小表现修复）；
5. 实现真实背包/装备/属性和挂机收益；
6. 完成一个可结算、可存档、可对拍的 PVE 副本；
7. 再扩技能、任务、宝箱、伙伴、宠物、活动和广告。

> 文件级改动顺序、工作包边界和验收门槛见《单机化后续修改实施方案》。其中“存档 V1”已提前到玩法扩展之前，避免当前隐式重置持续覆盖进度。

这套顺序能最快把项目从“本地 mock 能进界面”推进为“进度可保存、规则可验证、核心玩法可玩的单机游戏”。
